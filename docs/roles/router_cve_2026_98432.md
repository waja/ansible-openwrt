# CVE-2026-98432 mitigation role

This standalone role temporarily drops IPv4 TCP packets carrying IPv4 IP
options before they reach the vulnerable IPv4 TCP path. It is independent
of the standard router playbook and all other roles.

The role is implemented and runtime-validated on OpenWrt 25.12. Turris OS 9.x
on the classic Turris Omnia is an intended compatibility target, but it is
**not runtime-validated**. No live validation is required for this change:
the only available Omnia is a productive device and will not be used as a
test system. The documented Turris assessment is read-only and must not be
interpreted as proof of packet-path compatibility. Turris OS 9.x is based on
OpenWrt 24.10; Turris OS switched to nftables in 7.1. The role requires an enabled fw4 firewall
service and passes runtime version gates for nftables and the kernel. If
these prerequisites are not met (for example, fw3/iptables, disabled
firewall service, or a dumb AP/switch configuration), deployment fails
safely without changing firewall state. Turris OS 7.x and older are not
supported by this role.

## Standalone deployment

Run only this playbook against a selected router:

    ansible-playbook -i inventory.ini playbooks/cve-2026-98432.yml \
      --limit router1

The role detects the running kernel release. For known upstream stable
branches it compares the running version with the first fixed release:

| Kernel branch | First fixed release |
| --- | --- |
| 5.10 | 5.10.272 |
| 5.15 | 5.15.223 |
| 6.1 | 6.1.190 |
| 6.6 | 6.6.159 |
| 6.12 | 6.12.113 |
| 6.18 | 6.18.56 |
| 7.2 | 7.2.10 |
| 7.3 | 7.3-rc7 / stable successor |

A fixed kernel package that has been installed but not booted does **not**
remove the mitigation. Detection uses `uname -r`, so the workaround stays
active until the running kernel is fixed. The installed kernel package
version and patch classification are reported separately. If package
metadata claims a fixed kernel while the running kernel is still vulnerable,
the role reports `kernel_package_suggests_fixed_update: yes` as an advisory
signal. OpenWrt APK metadata can be stale or inconsistent with the running
kernel, so this does not prove that a fixed kernel image is ready to boot.
After reboot, a subsequent Ansible run detects the fixed running kernel and
removes only the role-owned UCI include, nftables file, and sysupgrade entry.

Unknown vendor kernels default to keeping the mitigation installed. Set
`router_cve_2026_98432_kernel_status: patched` only after verifying the
vendor's backport; use `vulnerable` to force the mitigation when automatic
version detection cannot classify a kernel. These overrides are Ansible
variables, not device state: persist a verified vendor assessment in the
appropriate `host_vars` or `group_vars` file. Supplying it only with
`-e` affects that invocation; a later run without the override returns to
automatic detection.

## State and verification

- `router_cve_2026_98432_state: auto` (default): install for vulnerable or
  unknown kernels; remove only when a known fixed kernel is running.
- `router_cve_2026_98432_state: present`: force the workaround, even when the
  running kernel is classified as patched.
- `router_cve_2026_98432_state: absent`: force removal, regardless of kernel
  classification.
- `router_cve_2026_98432_kernel_status: auto|patched|vulnerable`: automatic
  detection or an explicit vendor assessment.
- `router_cve_2026_98432_manage: false`: detection and current mitigation
  status only; no configuration is changed.

The role installs an isolated `ip cve_2026_98432` table using a UCI
nftables include at `ruleset-post`. The file starts with `destroy table`
for that exact owned table before declaring it again. This is required because
fw4 reloads can re-apply the ruleset-post include while the independent table
still exists. Before changing state, installation applies conservative
minimum-version gates of Linux 6.3+ and nftables 1.0.8+ for this syntax.
These checks are version gates, not a probe of every kernel/vendor
capability. The role validates with `fw4 check` before reloading, verifies
the active table and rule, and preserves the owned file through sysupgrade
in `/etc/sysupgrade.conf`.

The rule is:

    ip protocol tcp ip hdrlength 6-15 counter drop

It matches IPv4 IP options, not ordinary TCP options (MSS, SACK, timestamps).
IPv6 is not matched. The early prerouting hook is intended to cover router
INPUT and routed FORWARD traffic. Bridge/L2, hardware offload, XDP, tunnel,
CIPSO/NetLabel, and other bypass paths require platform-specific validation.

## Turris Omnia notes

Turris OS 9.x is based on OpenWrt 24.10 and supports the classic Turris Omnia.
Turris OS 7.1 was the release that switched the platform from iptables to
nftables. Do not infer the running kernel version or patch status from the
Turris OS release number. Detect the actual running kernel with `uname -r`
on the device and assess any vendor backport separately. The upstream 6.6
stable threshold of 6.6.159 applies only when the running vendor kernel is
equivalent to that upstream stable branch without a relevant backport. A
vendor-provided kernel may use a different version string or contain a
backport; record a `patched` override only after verifying the vendor's
security assessment.

A read-only inventory on a productive Turris Omnia running Turris OS 9.1.4
(kernel 6.6.156, ARMv7, Armada 385) confirmed the fw4/nftables framework
and `mvneta` Ethernet driver. It found no active software nftables
flowtable; `ethtool` reported `hw-tc-offload` and `l2-fwd-offload`
unavailable on eth1/eth2. The integrated switch's separate hardware
L3/NAT acceleration capabilities remain undetermined. No role installation,
firewall reload, packet-path test, offload activation, or reboot was
performed on that productive router. This inventory is not Turris packet-path
validation and does not establish support on Turris OS 9.x. This limitation
is explicitly accepted for this change; no test on the productive Omnia is
planned or required.

## Limitations

This is a temporary firewall mitigation, not a kernel fix. Legitimate IPv4
TCP traffic using IP options will be dropped. The role does not disable
MPTCP, change sysctls, or modify boot parameters.

Automatic detection is deliberately conservative: only listed upstream
stable branches are classified. Kernel release suffixes such as
`-turris` and `+deb` are ignored for upstream branch/version comparison;
unknown branches and malformed releases remain `unknown`. This cannot prove
whether a vendor has backported the fix. Unknown versions retain the
workaround until an operator supplies a verified, persistent assessment.
The upstream fixed-version table must be reviewed whenever the Linux kernel
CVE announcement is updated; vendor-specific backports must be assessed
separately.

## Removal

After confirming that the running kernel contains the upstream fix or a
verified vendor backport, run the standalone playbook with:

    ansible-playbook -i inventory.ini playbooks/cve-2026-98432.yml \
      --limit router1 -e router_cve_2026_98432_kernel_status=patched

Alternatively, the next invocation with `state: auto` removes the mitigation
automatically when the running kernel is in a known fixed range. An
installed-but-not-yet-booted kernel update does not trigger removal.

## Validation status

The following runtime validation is complete on a disposable OpenWrt 25.12.5
r33051-f5dae5ece4 VM (kernel 6.12.94, x86/64, QEMU i440FX):

- Install the role and verify the dedicated table, chain, hook and drop rule.
- Send TCP packets with IPv4 options through router INPUT and routed FORWARD;
  verify they are dropped and the mitigation counter increments.
- Send ordinary IPv4 TCP packets without IP options and verify they continue
  to work; also verify an ordinary IPv6 TCP connection.
- Run repeated `fw4 reload` operations and verify the table remains active.
- Reboot and verify the nftables file, UCI include, sysupgrade entry and
  active rule are restored.
- Enable software flow offloading, confirm the active nftables flowtable and
  `[OFFLOAD]` conntrack state, then repeat INPUT/FORWARD checks. An established
  offloaded TCP socket was also switched to IPv4 Record-Route options; the
  mitigation counter increased and the connection ceased to be marked
  offloaded. These observations apply only to the tested VM/kernel/software
  flowtable path.

The following limitations remain:

- Turris OS 9.x on the classic Turris Omnia is an intended compatibility
  target but has not received live install, reload, packet-path, reboot or
  removal validation. The only available Omnia is productive; testing it is
  explicitly out of scope and is not an acceptance requirement for this
  change. The read-only assessment above is not runtime validation. Treat
  Turris OS 9.x support as unverified until independently tested on suitable
  non-production hardware.
- Hardware flow offloading has not been tested on a platform with a confirmed
  hardware-offload datapath. Do not infer hardware-offload coverage from the
  software-flowtable test.

Do not interpret `fw4 check` alone as packet-path validation: it checks
ruleset validity, not whether real traffic traverses the intended hook.
